# Wake-Word Data Collection and Evaluation

Status: **First spoken corpus collected and evaluated; current model fails the gate**

## Purpose

The physical 96% versus 87% comparison showed roughly three detections per ten
attempts at both cutoffs. Threshold reduction is therefore not the production
fix. This workflow collects representative examples from Franky's real
microphones and room, evaluates the deployed model before retraining, and keeps
the privacy boundary explicit.

## Implemented collection path

The control board now has a **Dataset** area. Each sample follows an explicit
two-step flow:

1. The user selects the sample class, distance, and orientation.
2. The user presses **Record 3-second sample** and says the displayed phrase.
3. Firmware exports a bounded 16 kHz, 16-bit mono WAV source stream.
4. The sample remains only in browser memory while the user listens to it.
5. **Keep sample** writes it to local ignored storage. **Discard and retry**
   releases it without writing a file.

The diagnostic firmware captures `afe_fetch_result_t.data`, the same
post-ESP-SR-AFE mono signal supplied to the custom wake model. It does not use
the manual recorder's raw stereo/microphone mix proxy. The firmware disarms the
wake detector during the bounded capture and restores it afterward.

Kept files and JSON sidecars live below:

```text
tools/wake-word/.cache/recordings/
  positive/
  hard-negative/
```

That directory is ignored by Git. Filenames are generated by the loopback
service, never from browser text. Each sidecar records the fixed prompt ID,
conditions, format, capture pipeline, duration, signal levels, and SHA-256. It
does not record a speaker name, transcript, arbitrary filename, or audio bytes.

## Privacy and safety boundary

- No always-on or near-miss audio retention exists.
- Capture begins only after a deliberate button press and stops after three
  seconds.
- Nothing is written until the user explicitly keeps the previewed sample.
- The browser talks only to the loopback service and the USB board.
- Dataset mutations require a random per-process same-origin token.
- Uploads are limited to canonical 16 kHz mono PCM16 WAV, 0.5–5 seconds,
  256 KiB each, and 100 samples total.
- Individual deletion is available beside each saved sample. **Delete all**
  requires an explicit confirmation and permanently removes the local files.
- Collection does not automatically add recordings to training.

## Approved first corpus

- 30 positive **“Yo Franky”** samples, beginning at the failed-test condition
  of roughly 20 inches, facing Franky, in a quiet room. The guide varies natural
  pacing, level, pitch, and off-axis delivery without asking for theatrical
  speech.
- 20 hard negatives: ten phonetically similar phrases plus ten ordinary
  sentences that must not activate Franky.

Preserve each miss, awkward delivery, and representative everyday attempt.
Do not retain accidental household speech; discard and retry it.

## Offline evaluator

After samples are kept, run:

```powershell
cd tools/wake-word
.\.venv\Scripts\python.exe .\evaluate_recordings.py
```

The evaluator uses the deployed ignored `yo_franky.tflite` model and pinned
microWakeWord frontend. It recreates the firmware's three-feature-frame
inference cadence and five-result integer moving average, then reports positive
recall and hard-negative activation counts from 50% through 99%. It writes its
private JSON report to `.cache/evaluation/latest.json`.

Short negative clips support activation counts only. They do not establish
false activations per hour. Python-versus-board score parity also remains an
explicit validation item even though both paths use the same feature and
post-processing parameters.

## First corpus result — August 27, 2026

The user completed the guided set in one approximately ten-minute session. The
private corpus contains exactly 30 positive and 20 hard-negative WAV/metadata
pairs. All 50 WAV hashes match their sidecars, no duplicate audio hashes exist,
and every file uses `afe_processed_mono_v1`. Positive captures cover near,
20-inch, room, far, and off-axis conditions; 19 of the 20 hard negatives use
the original 20-inch facing condition.

| Cutoff | Positives detected | Hard-negative activations |
| ---: | ---: | ---: |
| 50% | 28/30 | 7/20 |
| 60% | 28/30 | 6/20 |
| 70% | 28/30 | 6/20 |
| 80% | 28/30 | 6/20 |
| 87% | 27/30 | 6/20 |
| 92% | 25/30 | 6/20 |
| 96% | 25/30 | 5/20 |
| 99% | 21/30 | 4/20 |

Positive peak scores range from 22–100% with a 100% median. Hard-negative
scores range from 3–100% with a 3% median, showing a bimodal negative set rather
than clean class separation. At 96%, the missed positives are the “look just
past Franky,” quick delivery, short-gap delivery, relaxed end-of-day, and final
representative samples. The final representative and “look just past” samples
remain below 50%.

At the same 96% cutoff, “Yo Frank,” “Yo Frankie boy,” “Go Franky,” and “Yo
friendly people” each score 100%; “You’re frankly mistaken” scores 97%. “Hello
Franky” is immediately below the cutoff at 95%. This is not explained by simple
recording level: low-scoring positives include loud captures, while 100%-scoring
hard negatives include quieter captures.

The current model fails this offline gate. Lowering the threshold recovers at
most three positives and increases hard-negative activations; raising it loses
four more positives while still accepting four hard negatives. Keep the flashed
default at 96% until a replacement model passes its own evidence gates.

## Current verification evidence

- **Built:** firmware with `wake_sample`, loopback storage API, browser Dataset
  workflow, and offline evaluator.
- **Automated:** Release build and 24 runtime tests pass; control-board
  JavaScript parses successfully; the evaluator completed against one generated
  canonical sample, which was deleted afterward.
- **Protocol-tested:** the flashed board advertised `wake_sample`, returned
  exactly 32,000 bytes for a one-second 16 kHz mono capture, and remained at the
  96% default with diagnostics off. The flashed 1,159,296-byte application image
  has SHA-256 `82E9CCA086F940FAFC86536B1ACC0CC4E6E0EB0AF59A81F5C0A1EDF82731EAD9`.
- **HTTP-tested:** an unauthorized write returned 401; an authorized canonical
  sample was saved, counted, deleted, and no longer counted.
- **Browser-observed:** the connected control board recognized the new firmware
  capability, rendered the guided Dataset area, and was used to review and keep
  the complete 50-sample corpus.
- **Corpus-verified:** 50 unique hash-valid WAV/metadata pairs were evaluated;
  the full threshold results are recorded above and the detailed report remains
  in ignored local storage.
- **Not yet observed:** exact board/Python score parity, an improved model, a
  fresh-session acceptance corpus, or improved wake reliability.

## Advancement gate

The current model has now been evaluated and its positive and hard-negative
scores overlap materially. Threshold tuning is closed as a production option,
and retraining with physical positives and hard negatives is justified.

Before training, establish score parity on representative shared samples using
the embedded board preprocessor and scorer. Preserve a declared split or,
preferably, use a later recording session as the untouched acceptance set; all
50 current recordings came from one session, so evaluating a candidate on data
it trained against would not prove improved physical reliability. A candidate
must then improve both positive recall and confusing-phrase rejection before it
is flashed for repeated-wake and idle false-activation testing.
