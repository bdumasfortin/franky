# Version 1 Product Definition

Status: **Approved direction; wake-to-assistant USB slice implemented**

## Goal

Deliver a small but genuinely useful personal voice assistant using the
Waveshare ESP32-S3 audio board and custom software running on the computer.

## Product boundary

- **Hardware:** Waveshare ESP32-S3-AUDIO-Board with no revision printed on the received sample.
- **Room endpoint:** onboard microphones, speaker, RGB ring, wake engine, and future buttons.
- **Compute host:** a custom .NET application running on the computer.
- **Target connection:** Wi-Fi for assistant traffic; USB for power, flashing, diagnostics, and the current development path.
- **Platform boundary:** standalone project-owned software, not the official Home Assistant platform.

## Experience

The development experience begins when the on-device **“Yo Franky”** model
detects the wake phrase. Franky acknowledges through the speaker and LED ring,
listens until the user stops speaking, and shows a locally generated transcript
in the control board. The same lifecycle was first verified using the “Hi ESP”
WakeNet fallback, and the custom phrase has now passed its first physical spoken
test as well. A later quiet-room test at roughly 20 inches found that the custom
phrase sometimes required about ten repetitions, so its current sensitivity is
not acceptable even though the downstream path worked correctly after a wake.

The control-board service now passes that transcript into the existing
conversation and safe-command pipeline and returns a structured action result
plus text response. The bridge is locally tested with the demo provider, and
both the local Ollama and optional OpenAI tool loops are covered with
deterministic HTTP tests. Live Ollama selected both read-only diagnostics
correctly through the loopback service. After successful physical wakes, both
diagnostics answered correctly and the longer negative control behaved as
expected. The first named device action is implemented and flashed: natural
questions about how Franky is doing request an embedded “SUUUPER” clip, and the
UI waits for firmware completion before reporting success. Direct board
acknowledgement, live Ollama selection, and audible physical playback are
verified. After one contraction variant failed to select the tool, common short
phrasings now use a deterministic local matcher before the model. Generated
response speech and the later Wi-Fi/WebSocket transport remain ahead.

## V1 non-goals

- General-purpose autonomous agent behavior.
- Unrestricted device or shell control.
- Multiple room satellites.
- Display, camera, battery, or mobile application support.
- Long-term personal memory.
- Production-grade acoustic tuning for every room condition.

## Success criteria

1. A developer can run the computer-side system from documented instructions without committing secrets.
2. One wake utterance travels from the board to the computer and becomes an accurate local transcript.
3. That transcript exercises the same conversation and action path already available through text input.
4. A response returns through the board speaker with truthful visual state feedback.
5. Initial read-only commands work reliably, while unknown commands and arbitrary arguments are rejected.
6. Failed or ambiguous commands do not perform an unintended action and produce a useful response.
7. Diagnostics identify the stage and reason when a request fails without persisting household speech by default.
8. The documentation states whenever audio or text crosses the local network boundary.
